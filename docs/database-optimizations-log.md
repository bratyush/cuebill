# Database Optimizations Log

**Date:** July 30, 2026  
**Context:** Based on the analysis of top queries executed on the Turso Database (exported from the Turso App dashboard), several performance bottlenecks were identified and resolved across the Drizzle ORM implementation.

---

## 1. Missing Database Indexes

**The Reason (Why):**
Analysis of the top queries revealed that the database was executing expensive full table scans for almost every read operation. Since this is a multi-tenant application, all queries filter data by the `club` column. Additionally, many queries join tables using foreign keys (e.g., `tableId`, `memberId`, `billId`, `itemId`). Without indexes, SQLite has to scan every row to find matches, leading to significantly degraded performance as data grows.

**What Happened (The Fix):**
We updated `db/schema.ts` and utilized Drizzle's `index()` utility to add explicit indexes to all tables. 
- Added an index on the `club` column for every table (`members`, `tables`, `transactions`, `bills`, `items`, `canteenBills`).
- Added indexes on all foreign key columns used in relations (e.g., `memberId` in bills and transactions, `tableId` in bills, `billId` and `itemId` in canteenBills).
- **Required Action:** A migration push (`yarn db:push`) is required to apply these indexes to the live Turso database.

## 2. In-Memory Data Filtering

**The Reason (Why):**
In `services/revenue-data.ts`, the application was fetching all canteen bills for a given club and then utilizing JavaScript's `.filter()` to discard rows outside of the specified date range. As the application accrues data over months and years, this approach would pull thousands of unnecessary rows into memory, causing severe latency and high memory usage on the backend server.

**What Happened (The Fix):**
We rewrote the query fetching `canteenBills`. Instead of using the relational API to fetch all records, we switched to the core query builder (`db.select()`) and performed an `innerJoin` on the `bills` and `items` tables. This allowed us to apply the date boundaries directly in the SQL `WHERE` clause, pushing the filtering workload back to the database where it belongs.

## 3. Overhead of Drizzle's Relational API

**The Reason (Why):**
The Turso dashboard showed several top queries using complex `json_array()` structures and nested subqueries. This is the underlying SQL generated by Drizzle ORM when using its Relational API (e.g., `db.query.table.findMany({ with: { relation: true } })`). While the Relational API is highly convenient, compiling relations into JSON structures can add unnecessary overhead in SQLite, especially when tables lack adequate indexes, creating performance drags on frequently hit endpoints.

**What Happened (The Fix):**
For the most frequently accessed endpoints, we replaced the Relational API calls with standard SQL joins using Drizzle's core query builder (`db.select().leftJoin(...)`). This generates flat, traditional SQL queries that SQLite and Turso execute and optimize much more efficiently.
- Refactored `services/revenue-data.ts` to use `leftJoin` for fetching bills with their associated tables and members.
- Refactored `services/revenue-data.ts` to use `leftJoin` for fetching transactions and their associated members.
- Refactored `app/api/bills/route.ts` to fetch bills and tables using `leftJoin`.
- Refactored `app/api/members/bills/[memberId]/route.ts` to fetch a member's bills and associated tables using `leftJoin`.
